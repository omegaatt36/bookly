# Project Architecture Overview

This project is organized as a monorepo to simplify development, maintenance, and deployment workflows. Below is a high-level overview to help future LLMs (and developers) quickly understand and navigate the system.

Monorepo Layout

- app/
  - api/         // Backend API implementation (Go)
  - web/         // Frontend implementation (Go + html/template + HTMX)
- domain/        // Domain entities and enums (business core)
- service/       // Service layer (business logic, application services)
- persistence/   // Database-related code, repository pattern, SQL
- doc/           // Documentation (OpenAPI/Swagger, architecture, etc.)
- build/, deploy/, cmd/, bin/, tmp/, etc. // Additional tooling & build assets
- go.mod, go.sum // Dependency management
- sqlc.yaml      // SQLC configuration for database code generation
- Taskfile.yml   // Tasks for development and automation

Key Directories and Their Purposes

/app/api/
Contains the backend code (in Go), organized into modules by features. This includes API routing, servers, middleware, and feature-specific code in subfolders (e.g., bookkeeping/, user/, engine/).

/app/web/
Implements the frontend using Go's html/template and HTMX for server-driven UI. Includes HTTP routing, middleware, template rendering, and interaction logic.

/persistence/
Handles database logic. Uses sqlc for type-safe Go code generation from SQL and schema definitions. Organized as follows:
- sqlc/      // Raw SQL queries and schema
- sqlcgen/   // Generated Go code (do not edit manually)
- database/  // (Optional) Database setup/utilities
- migration/ // Database migration scripts
- repository/ // Go repository implementations

/domain/
Defines the business/domain entities, core types, and enums. Pure logic without external dependencies or side effects, shared by both /app and /service layers.

/service/
Encapsulates business logic and use cases. Each subfolder corresponds to a core business domain (e.g., bookkeeping, auth, user). Services leverage domain models, repositories, and infrastructure integrations.

/doc/
Holds documentation files. Notably:
- openapi.yaml // OpenAPI/Swagger specification of backend APIs
- architecture.md // (this file) overall architecture description

Important Files

- go.mod / go.sum: Go dependencies.
- sqlc.yaml: Configuration for SQLC, specifying SQL sources and output directories.
- Taskfile.yml: Defines common tasks (testing, building, linting, compose workflows).

Tech Stack and Key Conventions

- Backend: Go (standard library, github.com/urfave/cli/v2, JWT, PGX for Postgres, etc.)
- Frontend: Go (html/template) + HTMX (for dynamic server-driven web UIs)
- Database: PostgreSQL; SQLC used for generating Go types/repositories from SQL
- Testing: Standard Go test framework, with testify where appropriate
- Task/Build Automation: Taskfile (task), Docker Compose for development
- Documentation: OpenAPI/Swagger (YAML)

Typical Workflow

1. API logic is implemented in /app/api. Business rules reside in /service and /domain.
2. Persistence is abstracted by repository interfaces. Actual database interaction is via code generated by SQLC using raw PostgreSQL and PGX driver.
3. The frontend in /app/web renders UI using Go templates and HTMX, communicating with the backend via HTTP.
4. Domain and service code are shared and reused across both API and web layers for consistent logic.

This structure is intended to enable clear separation of concerns:
- domain: "what" the business does
- service: "how" the application realizes use cases
- persistence: "where/how" the data is stored and retrieved
- api/web: HTTP interfaces, presentation logic

Refer to ./doc/openapi.yaml for detailed API documentation. Refer to Taskfile.yml for common development scripts and workflows.

For any further clarifications, explore each module's README or code comments.
